## The problem

I wanted a personal AI setup that runs day-to-day without babysitting: distinct
spaces for different parts of my life, memory that persists across sessions,
health data captured automatically, and old data cleaned up on its own.

## What it is now

Agento is a Pi-based stack, not a Discord bot fleet. ONE container runs one `pi`
process for a single **chat** profile, fronted by a `pi-gateway` that serves the
OpenAI-compatible surface the app already speaks. The agent's workspace, skills,
and credential scope all live in that one profile.

The frontend is the **Agento Android app** (Jetpack Compose) — the app is Agento's
front end, not a separate product. A single Chat tab carries threaded,
on-device-persisted conversations with attachments; the rest of the surface is
Projects, Task Manager (tasks, due-time reminders and a home-screen widget),
Files, Scheduler, Skills, Tools and Settings. One Server URL + Password — the app
talks to an nginx proxy (`:8080`) that routes `/p/*` to the Pi gateway's
OpenAI-compatible chat API (`:8643`) and `/api/*` to the health-sync service.

The agent reasons through **OpenCode Go directly** (`mimo-v2.6-flash`), with the
model and reasoning effort picked in Settings from the live gateway catalog.
Domain capabilities come from eight Go MCP servers I wrote — money, cookbook,
health-check, task-manager, project-manager, notes, memory and browser (headless
Chromium, where each domain holds for approval before it loads). No LLM proxy and
no failover chain: one provider, one request path, so there is nothing to fail
over from.

Chat turns are server-side **runs**: killing the app mid-reply no longer kills
the work — reopening the thread picks up the same run, with steer-while-running,
stop, and a runs list per thread. A reply that finished while the app was closed
is adopted into the thread instead of being lost. Voice works as a **live call
mode** with barge-in — interrupting the readout steers the turn instead of
talking over it. The agent can also pause mid-turn to **ask a question**: an
inline card with buttons or a free-text field, and the turn waits for the answer.

Sensitive agent actions (money writes, deletes, destructive rewrites) pause behind
**approval gates** — the turn holds, the app raises a badged Approvals entry with
redacted arguments plus an audit trail, and deny fails the call back as a tool
error. The agent also carries **durable memory** (facts land pending, are
confirmed on the Memory screen, then inject into the prompt) and **taught skills**
(any conversation can become a tested, activatable draft skill, invoked from the
composer's `/` menu or scheduled as a cron routine). Task changes go into a
90-day change log — what changed and when — that outlives the three-day TTL on
completed tasks.

## How it runs

One Podman Compose file: pi, health-api, proxy, and a one-shot retention job.
Health Connect syncs (steps, sleep, workouts) flow from the app through health-api
into per-day MongoDB docs on an hourly WorkManager cadence (configurable 1–24h).
Every night at 03:00 the retention binary prunes money transactions older than 90
days and health logs older than 30 days — while weight, notes and cookbook data
are permanent. Dev checkouts point at a throwaway Atlas database, so production
data is never at risk. A `hermes.sh` CLI (`init|start|stop|restart|status|clean`)
— the name is a leftover from the Hermes era — orchestrates the whole lifecycle,
and every app change ships a versioned release APK with in-app updates.

## What it taught me

Multiplexing lost to maintenance: the stack began as one gateway with three scoped
profiles and converged on a single chat profile in a single container. And
reliability is designed, not hoped for — approval-gated writes, automated pruning,
and a single secret store (the git-ignored `.env`) matter more than model choice.
Most of this system exists so that nothing pages me.
