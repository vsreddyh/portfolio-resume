## How it works

Two halves, one database.

The Android app is a thin client: tasks, projects, files, mail reports, Health Connect sync, settings. It knows one server URL and one password. An nginx proxy routes `/api/*` to `health-api`, which owns sync and storage on MongoDB Atlas.

The agent runs on the host in T3 Code, not in the app and not in a container. Six Go MCP servers I wrote — task, project, money, cookbook, health-check, reports — read and write the same collections the phone reads. Gmail goes through one extra server, read and label changes only.

I built the chat myself twice before this: a Hermes runtime, then a Pi container with runs, approvals, memory, skills and voice. Both worked. Both were a second chatbot to maintain, with a matching set of app screens for every feature. I deleted them over #487–#495 and kept the domain servers, which were the only part that was mine. T3 Code already does turns, permissions and tool loops.

Retention runs on cron and on stack start: money after 90 days, meals and day logs after 30, read and unstarred reports after 7. Weight, notes and cookbook data stay. Dev checkouts point at a throwaway Atlas database.

## Limits

Scoped to one user and one phone by design — the data model, single-password auth, and retention windows all assume a single owner. The agent side lives wherever T3 Code is installed, so a new machine means reinstalling the host side. iOS and multi-user sharing are the natural next steps, needing real auth rather than the current single-password model.
