## The problem

I wanted a personal AI setup that runs day-to-day without babysitting: distinct
spaces for different parts of my life, health data captured automatically, and
old data cleaned up on its own. The app was the interesting part; the agent was
supposed to be the easy part.

## What it is now

Two halves that share one database.

The **Agento Android app** (Jetpack Compose) is a thin client: Tasks/Projects,
a Task Manager with due-time reminders and a home-screen widget, Files, ∃-Mail
(reports), Health Connect sync and Settings. One Server URL + one Password, and
it talks to an nginx proxy (`:8080`) that routes `/api/*` and `/health` to
`health-api` (`:8001`), which owns sync, tasks, projects, files and reports on
MongoDB Atlas.

The **agent is not in the app and not in a container**. It runs on the host in
**T3 Code**, configured from the repo (`opencode.json` + `.opencode/`), and it
reaches the same Atlas database through six Go MCP servers I wrote —
`task-manager`, `project-manager`, `miser-money`, `cookbook`, `health-check`,
`reports` — built into local binaries and launched through a wrapper that loads
`MONGODB_URI`/`MONGODB_DB` from the root `.env`. One external server handles
Gmail as read + label changes only; there is no send, draft or filter management.

## The part I deleted

I built the chat myself, more than once.

First a **Hermes** runtime with the conversation loop, transcripts and scheduled
chats in my own process. Then a **Pi** container: a `pi-gateway` serving an
OpenAI-compatible surface over SSE, resumable runs that survived the app being
killed, in-process approval holds with an in-app approval queue, durable memory,
user-taught skills, live voice with barge-in, and Gmail/Calendar OAuth
connectors. Later I ran the same idea on **opencode** as the proxy in front of
the model.

Every version worked. None of them were worth keeping. What I was maintaining
was a worse version of a chat client: turn plumbing, streaming, approvals,
memory, a skill editor, a voice mode, reconnect logic — and every feature needed
a matching screen in the app. The domain tools were the only part that was
actually mine.

So I dropped it. Chat, scheduled chats, runs, approval gates, memory, skills,
voice and the connector store were removed over #487–#495, with the container,
the gateway packages and the app screens deleted bottom-up. **T3 Code was simply
the better alternative**: a harness that already does turns, permissions and
tool loops, kept up to date by someone else.

What I kept is the part that had value: the six domain servers are now wired
into T3 Code directly. The agent asks `miser-money` to log a transaction,
`task-manager` to move a task, `health-check` to read the last 30 days of sleep —
and hits the same collections the phone reads. Approvals became T3 Code's
permission prompts (`*delete*`, `*log_transaction*`, `*modify_gmail_message_labels*`
all ask), and the audit trail is a Mongo row instead of an in-app queue.

## How it runs

One Podman Compose file with three services: `health-api`, the nginx `proxy`, and
a one-shot `retention` job. Health Connect data flows from the app through
`health-api` into per-day MongoDB docs on an hourly WorkManager cadence
(configurable 1–24h). Retention runs on host cron and once on stack start: money
older than 90 days, meals and day logs older than 30, read and unstarred reports
after 7 — while weight, notes and cookbook data are permanent. Dev checkouts
point at a throwaway Atlas database, so production data is never at risk.

`hermes.sh` (`init|start|stop|restart|status|clean`) still orchestrates the stack;
the name is a leftover from the runtime it used to start. Every app change ships a
versioned release APK with in-app updates.

## What it taught me

Multiplexing lost to maintenance twice: first from three scoped profiles down to
one, then from a whole agent deployment down to nothing but a host command. The
tell was that deleting features made the product better — the app got smaller,
the stack got smaller, and the agent got capabilities I had spent weeks failing to
build well.

The rule I take from it: build the tools that are yours, rent the harness that
isn't. And reliability is designed, not hoped for — permission prompts on the
destructive paths, automated pruning per domain, and a single secret store matter
more than which model answers.
