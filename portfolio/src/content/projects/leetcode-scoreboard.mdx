## The problem

Counting solved problems rewards grinding easies. For a practice group, the
fair score pays more for harder problems — and the board has to stay fast and
fresh without hammering LeetCode on every page view.

## What I built

Score per accepted problem is `100 − acceptance rate`, bucketed per user per
day in IST. The key decision is the write/read split: an external cron hits
`/api/sync` every 5 minutes (admin cookie or a constant-time-compared
`CRON_SECRET`), which walks tracked users through `recentSubmissionList`,
upserts one doc per user+question with the score pinned at first accept, and
backfills canonical per-question rates so solving minutes apart pays the same.
An end-of-day refresh folds into the first tick after 23:30 IST. The dashboard
reads pre-aggregated Mongo data only — it never calls LeetCode — and each sync
with new solves pushes a summary (solver counts, today's points, leader) via
Web Push, pruning dead subscriptions automatically.

Around it: a password-cookie admin panel with HMAC-signed sessions for tracked
users and manual syncs, PWA install support, and dark/light theming.

## What it taught me

Separate the hot path from the slow source. Polling external APIs on a timer
into your own store, then serving reads from the store, is a pattern that
scales from scoreboards to trading infra — and idempotent upserts plus
canonical scores are what keep concurrent writers honest.
